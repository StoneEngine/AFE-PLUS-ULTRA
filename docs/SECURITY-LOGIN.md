# การป้องกันการเดารหัสผ่าน — หน้าเข้าสู่ระบบเจ้าหน้าที่

เอกสารนี้ตอบ OWASP ASVS 5.0 ข้อ 6.1.1 (เอกสารต้องบอกว่าใช้กลไกจำกัดจำนวนครั้งอย่างไร ตั้งค่าอย่างไร และกันการกลั่นแกล้งให้บัญชีถูกล็อกอย่างไร)
และเป็นเกณฑ์ที่โค้ดต้องทำตามในข้อ 6.3.1

## ใช้กับอะไร
- `POST /api/auth/login` (หน้าเข้าสู่ระบบเจ้าหน้าที่ `/admin/login`) — บัญชีที่ใช้รหัสผ่าน
- ผู้ดูแลและผู้มีภาวะพึ่งพิงเข้าใช้ผ่าน LINE (LINE ID Token) ไม่ได้ใช้รหัสผ่านกับระบบนี้ จึงไม่อยู่ในเอกสารนี้

## กลไก (โค้ด `src/lib/loginRateLimit.ts`)
| ค่า | ตั้งไว้ | ตัวแปรในโค้ด |
|---|---|---|
| นับอะไร | ครั้งที่เข้าสู่ระบบไม่สำเร็จ (ไม่มีชื่อผู้ใช้นี้ หรือรหัสผิด หรือรหัสยาวเกินที่รับ) | `recordFail` |
| นับแยกตาม | คู่ ชื่อผู้ใช้ + IP ของผู้ส่ง (อ่านจาก header `X-Real-IP` แล้วค่อย `X-Forwarded-For` ที่ Railway ส่งต่อมา) | `keyOf` `clientIp` |
| ผิดได้กี่ครั้ง | 5 ครั้ง ภายใน 15 นาที | `MAX_FAILS` `WINDOW_MS` |
| ผิดครบแล้ว | คู่นั้นถูกพัก 15 นาที ตอบ HTTP 429 พร้อม header `Retry-After` (วินาทีที่ต้องรอ) แม้ใส่รหัสถูกก็ยังเข้าไม่ได้จนพ้นเวลา | `BLOCK_MS` `secondsBlocked` |
| เข้าสู่ระบบสำเร็จ | ล้างตัวนับของคู่นั้น | `recordSuccess` |

## กันการกลั่นแกล้งให้บัญชีคนอื่นถูกล็อก (malicious account lockout)
- ไม่ล็อกบัญชีทั้งบัญชี พักเฉพาะคู่ ชื่อผู้ใช้ + IP ที่ใส่ผิด
- ถ้าคนอื่นตั้งใจใส่รหัสผิดเพื่อแกล้ง เจ้าของบัญชีที่เข้าจาก IP ของตัวเองยังเข้าสู่ระบบได้ตามปกติ
- การพักหมดเองใน 15 นาที ไม่ต้องให้ผู้ดูแลระบบปลดล็อก

## รหัสผ่าน (ASVS 6.2.8 · โค้ด `src/lib/passwordPolicy.ts`)
- bcrypt ใช้แค่ 72 ไบต์แรก ระบบจึงไม่รับรหัสที่ยาวเกิน 72 ไบต์ หรือมีไบต์ 0 ทั้งตอนตั้งรหัส (`admin/addAdmin` `auth/resetPasswordAdmin`) และตอนเข้าสู่ระบบ รหัสที่รับจึงถูกตรวจครบทุกตัว ไม่ถูกตัดท้าย
- ตอนตั้งหรือเปลี่ยนรหัสผ่าน (`admin/addAdmin` `auth/resetPasswordAdmin` `registration/create`) ไม่รับรหัสที่อยู่ในรายการรหัสผ่านที่คนใช้บ่อย 10,000 ตัว (`newPasswordProblem` · รายการ SecLists `src/lib/data/common-passwords.json`) ตาม ASVS 6.2.4 · ไม่ตรวจรายการนี้ตอนเข้าสู่ระบบ

## Session ของเจ้าหน้าที่ (ASVS 7.2.4 7.4.1 7.4.2 · โค้ด `src/lib/authMiddleware.ts` `src/pages/api/auth/logout.ts`)
- เข้าสู่ระบบสำเร็จ: สุ่มเลข session ใหม่ 256 บิต เก็บที่ `users.users_token` และใส่ใน JWT (`jti`) JWT ใบก่อนของบัญชีเดียวกันใช้ไม่ได้ทันที (เข้าสู่ระบบได้ทีละเครื่อง)
- ทุกคำขอ: `authMiddleware` ตรวจลายเซ็น (HS256) วันหมดอายุ และตรวจกับฐานข้อมูลว่า `jti` ตรงกับเลขล่าสุด และบัญชียังเป็นเจ้าหน้าที่ที่เปิดใช้
- ออกจากระบบ: หน้าเว็บเรียก `POST /api/auth/logout` เซิร์ฟเวอร์ล้าง `users_token` และส่ง `Clear-Site-Data`
- เปลี่ยนสถานะผู้ใช้ (`admin/updateUserStatus`): ล้าง `users_token` ของคนนั้น session เดิมใช้ไม่ได้ทันที

## ที่มาของการออกแบบ
- OWASP Authentication Cheat Sheet หัวข้อ Account Lockout แนะนำให้นับครั้งที่ผิดตามบัญชี ไม่ใช่ตาม IP และเตือนว่าการล็อกบัญชีอาจถูกใช้แกล้งให้คนอื่นเข้าไม่ได้
- ASVS 6.1.1 บังคับให้เอกสารบอกว่ากันการกลั่นแกล้งให้บัญชีถูกล็อกอย่างไร
- ระบบนี้เลือกนับตามคู่ ชื่อผู้ใช้ + IP เพื่อทำตาม ASVS 6.1.1 (ไม่มีหน้า "ลืมรหัสผ่าน" ให้ใช้เป็นทางออกตามที่ cheat sheet เสนอ) ข้อเสียที่ต้องยอมรับอยู่ในหัวข้อถัดไป

## ข้อจำกัดที่รู้อยู่
- ตัวนับเก็บในหน่วยความจำของเซิร์ฟเวอร์ ถ้าเซิร์ฟเวอร์ restart หรือ deploy ใหม่ ตัวนับเริ่มใหม่
- ผู้โจมตีที่ใช้ IP จำนวนมากพร้อมกัน (credential stuffing แบบกระจาย) ได้ลอง 5 ครั้งต่อ IP ต่อชื่อผู้ใช้ กลไกนี้ไม่ได้กันกรณีนี้ทั้งหมด
- ยังไม่ได้ตรวจว่าผู้ส่งปลอม header `X-Real-IP` / `X-Forwarded-For` ผ่าน Railway ได้หรือไม่
